# Analytics — Calculation Guide (every block, every filter)

**Who this is for:** property owners, support, and product. It explains, block by block, **exactly what
each number means, how the code calculates it, how the date filter changes it, and every assumption made.**
It is written to match the code precisely — if the screen and this guide ever disagree, that's a bug.

---

## How to read this guide

Every number is **one of three kinds**. This is the single most important thing to understand:

- **Live** — a snapshot of *right now* ("as of today"). **It ignores the date filter completely.**
- **Period** — counts what happened *inside the window you picked* with the filter.
- **Forecast** — looks *ahead*; uses its own forward window, not the top filter.

**The date filter options** and the window each one means:
- **Today** = just today.
- **This Month** = 1st of this month → **today** (month-to-date, not the whole month).
- **Last Month** = the full previous calendar month.
- **Current FY** = Indian financial year so far (1 Apr → today).
- **Custom** = any two dates you choose (upper end never goes past today for money blocks).
- **All Time** = no date limit.
- **Coming up** = tomorrow → a future date (forward blocks only).
- **Now** = (Occupancy only) the live snapshot.

**Status codes used throughout** (so support can trace a number):
- Tenant status: **0** = moved out, **1** = active/living, **2** = booking, **3** = lead.
- Invoice status: **0** = not paid, **1** = paid, **2** = partially paid, **3** = refunded, **4** = loss.
- Money is shown short: ₹1.8L, ₹3.29Cr. Counts are plain numbers.

# DUES

**"Dues" = unpaid bills.** The shared base pool for this tab is: invoices with **status = 0 (not paid)**,
active, amount ≥ ₹1, whose tenant is **active or a booking (status 1 or 2)**. Moved-out (status 0) tenants
are excluded from this base *except* where a block says otherwise. Filter options: This Month · Last Month ·
Current FY · Custom · All Time.

### Overview (the 6 tiles)
**What it shows:** a headline strip of the dues position. **Every tile has its own fixed window and
ignores the top filter.**
**How each is calculated (all on the base pool, by the bill's due date):**
- **All Time Dues** — every unpaid bill, no date limit.
- **All Past Dues** — unpaid bills whose due date is **before the 1st of this month**.
- **{Month}'s Due** — unpaid bills due **from the 1st of this month to today**. Carries a change chip vs
  the **same number of days into last month**.
- **All Future Dues** — unpaid bills due **after today**.
- **{Month}'s Projected Due** *(Forecast)* — what the recurring setup will **still raise before month-end**,
  which is **rent + every other recurring type, not rent alone**:
  1. **Rent** of living tenants (status 1) billed monthly (`rental_frequency = 2`, auto-rent on, rent not
     disabled) whose rent day falls **after today, on or before month-end**, and whose rent bill isn't
     already raised.
  2. **Packages** (food / services / any recurring due-type) whose scheduler entry is still pending and
     dated in the remaining window — valued at the amount that will be billed.
- **Current FY Dues** — unpaid bills due within this financial year. Chip vs the **same point last FY**.
**Assumptions:** change chips compare the *same elapsed days* of the previous period. Projected excludes
metered/variable types (electricity/water) unless the scheduler already holds a fixed amount, and assumes
rent isn't also set up as a package (would otherwise double-count — rare).

### Dues (Live)
**What it shows:** all money owed **right now**, split by how urgent it is. **Live — ignores the filter.**
**How it's calculated:** the whole base unpaid pool, bucketed by due date vs today — **Overdue** (due date
already passed), **Due Today**, **Due This Week** (next 7 days), **Due Later** (after that).

### Bills Summary
**What it shows:** for the selected window, how much came due and how much of it was collected. **Period.**
**How it's calculated:** **Bill Due** = sum of every bill that came due in the window (paid or not — invoice
status 0, 1 or 2). **Received** = the collected portion of *those same bills* (their paid amount). The gap
is what's still to collect.
**Assumption:** "This Month" is month-to-date (1st → today) so it reconciles with the {Month}'s Due tile
and the dues list, instead of counting bills that fall due later this month.

### Dues Breakdown
**What it shows:** the window's unpaid dues sliced three ways (tap to switch). Has its **own date dropdown**.
**Period.**
**How it's calculated:**
- **Category** — base pool grouped by bill type (rent, deposit, electricity…), case-insensitive; top 5,
  the rest folded into **Others** (tap opens the full list).
- **Tenant Status** — **wider than the base**: this is the only place moved-out tenants appear. Splits
  unpaid dues into **Active (not under notice)**, **Under notice** (living tenant with an eviction date),
  **Bookings** (status 2), **Old tenants** (status 0).
- **Added By** — base pool grouped by **who raised the bill** (Owner / RentOk / Partner / Customer /
  Tenant); top 4 + Others.
**Assumption:** "Added By" is **role-level only** — per-person attribution isn't stored.

### Overdue Breakup (Defaulters)
**What it shows:** the overdue pile **as of today**, two ways. **Live** — its dropdown only offers "All
Time" because overdue is always the full live picture.
**How it's calculated:** the base pool where **due date < today**. **By Amount** = aging buckets by days
late (1-7 / 8-14 / 15-21 / 22-90 / 90+, where days late = today − due date). **By Category** = grouped by
bill type, top 5 + Others.
**Assumption:** if there are bills but none overdue it shows a **"all paid on time"** healthy message; if
nothing was ever billed it shows an empty state — the two are deliberately different.

### Deposit Dues
**What it shows:** deposit money held vs still owed. **Live.**
**How it's calculated:** **Received** = deposit actually collected and still held — paid deposit/caution
invoices (status 1) **minus refunds and deposit-adjustment payments (mode 211)**. **Due** = deposit bills
still unpaid (base pool filtered to Security Deposit / Caution Money).

### Breakup by Stay Duration
**What it shows:** the window's unpaid dues split by tenant stay length. **Period.**
**How it's calculated:** base pool split into **Short-term** vs **Long-term** using the tenant's
short-term flag. Segments that are ₹0 are dropped.

### Dues by Property
**What it shows:** the window's unpaid dues per property, ranked. **Period.**
**How it's calculated:** base pool grouped by property, sorted high→low; each row shows a bar (relative to
the top property) and its **share of the account total**. Properties with ₹0 are included at the bottom.

### Upcoming Dues
**What it shows:** rent that will be billed later **this month** but isn't yet. **Forecast.**
**How it's calculated:** monthly living tenants (as in Projected Due) whose rent day is from tomorrow to
month-end and whose rent bill hasn't been raised, grouped by date. Only the **Rent** tab is populated
today; Food/Others appear only when configured.

# COLLECTION

**"Collection" = money received.** The base is every successful payment, joined to the bill it paid.
**Two views** (toggle): **Paid Date** reads money by *when it arrived*; **Due Date** reads by *when the
bill was due*. How a payment is valued: **deposit/advance/caution adjustments count as ₹0 new money**; a
**true advance** (payment against no bill) is valued at the payment's net amount; everything else is valued
at the bill amount. Filter: This Month · Last Month · Current FY · Custom · All Time · Coming up.
**Assumption:** the Paid-Date window never runs past today (money can't arrive in the future); the Due-Date
window keeps the full period.

### Collection Overview
**What it shows:** the headline collection position for the window. **Period, with two live tiles.**
**How it's calculated —**
- **Paid Date view (7 tiles):** **Total Collection** = all money received in the window. It then splits
  Total by the due date of each bill the money cleared: **{Month}'s Bills Collected** (bill due in the
  window), **Past Dues Collected** (bill due before it), **Paid Early** (bill due after it), **Advance**
  (payment against no bill). Plus **Current FY** (money received this FY) and **Settlement Pending**
  *(Live)*.
- **Due Date view (6 tiles):** **Billed** = everything billed in the window (invoice status 0 or 1),
  **Collected & Adjusted** = money + deposit/advance adjustments applied to those bills, **Still Unpaid** =
  Billed − Collected & Adjusted. Plus **Advance**, **Current FY**, **Settlement Pending**.
**Assumptions:** Billed is restricted to status 0/1 so **Still Unpaid equals exactly the not-paid amount**
(loss/operational invoices are excluded). On **Coming up** in Paid Date view, money can't have arrived, so
the tab shows a "switch to Due Date" message. Change chips compare the previous equal-length period.

### Collection Breakup
**What it shows:** the window's collection sliced four ways (tap to switch). **Period.**
**How it's calculated:** **Category** (by bill type), **Status** (by the payer's tenant state), **Mode**
(cash / UPI / bank / cheque / **RentOk** for online), **Received by** (who took the payment). Top 3 + Others.
**Assumptions:** online-via-RentOk payments collapse to a single "RentOk"; adjustment modes are excluded
from Mode/Received-by; a payment with no matched tenant stays in the total but not in the Status split; a
blank receiver shows as "Not recorded".

### Collection Status
**What it shows:** *(Paid Date only)* the window's collection by which bill it cleared. **Period.**
**How it's calculated:** the same four paid-date buckets as Overview — this-month due / past due / future
due / advance. Hidden in Due Date view.

### Adjusted Collection
**What it shows:** bills cleared **without new cash**. **Period (by paid date).**
**How it's calculated:** **Advance** (payment mode 288), **Security Deposit** (211), **Caution Money**
(291), and **Discount** (the discount recorded on invoices in the window).

### Collection Trend
**What it shows:** collection over time. **Its own range (8 weeks / 6 / 12 months), ignores the top filter.**
**How it's calculated:** each bar = **Collection** vs **Billed** (Paid Date view: money that arrived vs
what was billed that period) or **Collection** vs **Uncollected** (Due Date view: collected vs the still-
unpaid part of that period's bills). Current period is marked in-progress.

### Collection by Property
**What it shows:** the window's collection per property, ranked. **Period. Shown only with 2+ properties.**
**How it's calculated:** collection grouped by property (paid-date or due-date depending on view), sorted
high→low, with each property's share of the total.

### Payment Settlement
**What it shows:** online money and whether it reached the bank. **Its own dropdown.**
**How it's calculated:** **Collected via RentOk** = online payments in the window; **Total Settled** = the
part with a confirmed settlement (a successful payout, wallet UTR, or scheduler success); **Unsettled** =
collected − settled. Also lists which bank account settled money went to.
**Assumption:** online money with no settlement record is counted as **Unsettled** (flagged as a possible
data gap, not necessarily truly unsettled).

# EXPENSE

**"Expense" = money the property spent.** Base: active expenses with amount > 0. Filter: This Month · Last
Month · Current FY · Custom · All Time. **Assumption:** the window's upper end never goes past today (a
future-dated expense isn't counted before its date).

### Expense Overview
**What it shows:** the spend headline. **Period, with one live tile.**
**How it's calculated:** **Total Expense** = spend in the window; **Number of expenses** = count of
expense entries in the window; **Current FY Expense** = spend this FY; **Still owed to staff** *(Live)* =
money the business still owes staff who paid from their own pocket, read from the team passbook (personal-
funds fronted minus reimbursed).
**Assumption:** the money chip treats *up = bad* (more spend, red); the count chip is neutral.

### Expense Breakdown
**What it shows:** the window's spend split two ways. **Period.**
**How it's calculated:** **Category** — grouped into Salary / Maintenance / Rent / Electricity / Food and
Mess / Deposit Refunds (by name prefix), anything else keeps its own name, blank = "No category"; top 3 +
Others. **Payment Mode** — cash / G Pay / UPI / bank / cheque etc., with **FlexiPe** pulled out as its own
row and unknown modes shown as "Online".

### Top Payers and Vendors
**What it shows:** the window's spend by person. **Period.**
**How it's calculated:** **Paid by** (who paid) and **Paid to** (vendor/payee); blanks show as "No payer/
payee recorded"; top 3 + Others.

### Expense Trend
**What it shows:** spend per month. **Its own range (6 / 12 / 24 months), ignores the top filter.**
**How it's calculated:** total spend grouped by month; the current month is marked in-progress (a shorter
bar because the month isn't over).

### Expenses by Property
**What it shows:** the window's spend per property, ranked. **Period. Shown only with 2+ properties.**
**How it's calculated:** spend grouped by property, sorted high→low, with each property's share.
**Assumption (whole tab):** zero/negative-amount rows are excluded from spend (surfaced separately in the
View-all sheet); "no bill/receipt" means the expense has no attached bill file.

# OCCUPANCY (Inventory)

**How full the property is.** **View toggle:** Bed vs Unit (room). **The occupancy rate is always measured
by beds.** Rentable = total − disabled. Filter: **Now** (default) · This Month · Last Month · Current FY ·
Custom · Coming up.

**How the filter behaves here (important):**
- **Now** *(Live)* = the live snapshot from the same source as the rooms list and home screen.
- **A past period** *(Period)* = the **day-weighted average** — how full you were on an average day across
  that window (a bed filled for half the month counts as half a bed). This is **not** a single day's reading.
- **Coming up** *(Forecast)* = a projection from confirmed move-outs and confirmed arrivals only.

### Occupancy Overview (5 tiles)
**What it shows:** Rentable · Occupied · Occupancy Rate · Vacant · Under Notice.
**How it's calculated:** **Now** uses the live widget counts. A **period** uses average occupied beds =
(sum of occupied bed-days in the window ÷ days in the window); Vacant = rentable − occupied; the rate is
avg occupied beds ÷ rentable beds. **Coming up** = today's occupied − confirmed move-outs before the date
+ confirmed arrivals before it. **Under Notice** is always the live "as of today" number.
**Assumptions:** unit-view period counts are the bed average scaled by today's room-to-bed ratio
(approximate); the rentable denominator uses today's rentable count for past periods.

### Occupancy Status
**What it shows:** the live donut + summary chips + money tiles. **Live.**
**How it's calculated:** donut = **Occupied / Semi-Vacant (unit view) / Vacant / Disabled**. **Vacant is
split** into **booked** and **available**: booked = booking rooms minus those sitting behind an
under-notice tenant (so a re-booked under-notice bed isn't double-counted), clamped to the vacant count;
available = vacant − booked. Money tiles: **Avg Rent per Occupied** = total active rent ÷ occupied count;
**Avg Revenue per Rentable** = total active rent ÷ rentable count — it's lower whenever anything is vacant,
and the gap is the cost of vacancy.
**Assumptions:** the rent total only sums tenants who have a rent amount set, so where rent is sparsely
recorded the averages read low; the booked split is room-level (there's no booked-beds signal).

### Vacant Room Status
**What it shows:** empty rooms by how long they've been empty. **Live.**
**How it's calculated:** empty rooms are those the live view calls vacant (no active tenant, not disabled).
Each is aged by **today − the last tenant's move-out date**, floored at any date the room was re-enabled
after being disabled, into buckets **0-7 / 8-15 / 16-30 / 31+ days**. **Never rented** = a rentable room
with no stay history at all; **Unknown** = it was let before move-out tracking existed. The tallest bar is
shown red, the rest blue.
**Assumptions:** this is room-level; a room deleted before change-logging began can't be aged and is
dropped; a room with even one tenant never appears here (its free beds still count as vacant on the tiles).

### Upcoming Vacancy
**What it shows:** beds/rooms freeing up soon. **Forecast (from today onwards).**
**How it's calculated:** living tenants (status 1) with a **future, manager-accepted** eviction date,
bucketed by when — 0-7 / 8-15 / 16-30 / 31+ days. **Bed view** counts each departing tenant (beds); **Unit
view** counts distinct room-vacancy events (same room, same day = one).
**Assumption:** a tenant-raised notice that a manager hasn't accepted has no confirmed date and is
**excluded**.

### Agreements Ending Soon
**What it shows:** long-term agreements expiring soon. **Forecast.**
**How it's calculated:** active long-term tenants whose agreement end date falls in **30 / 60 / 90 days**.
The end date uses a 4-step rule: a recorded renewal date → the tenant's own agreement period → the
property's default → **11 months** if nothing is set.

### Occupancy Trend
**What it shows:** occupancy month by month. **Its own range (6 / 12 / 24 months), ignores the top filter.**
**How it's calculated:** each month is the **day-weighted average** — occupied unit-days ÷ days, against the
rentable capacity **as it stood that month** (rooms only count from when they were created; deleted/disabled
rooms are removed for the days they didn't exist). Occupied + Vacant always add to that month's total, so it
**never exceeds 100%**; the % headline matches the bar.
**Assumptions:** unit (room) view is exact; **bed view is approximate** where historical bed-level detail is
incomplete (it self-corrects as new stays record the bed); rooms deleted before change-logging began, and
disable dates from before it, aren't fully known — a small, shrinking gap.

### Where am I losing money?
**What it shows:** the rent lost to empty beds, by room type. **Live.**
**How it's calculated:** vacant beds grouped by sharing type (Single / Double / Triple / 4+); revenue loss
= vacant beds × the room's per-bed rent (its own tenants' average, falling back to the group average).
**Assumption:** Days-to-Fill is not computed yet (needs a room-emptied date the system doesn't record); a
coverage line states how many rooms had a rent set.

### Property Wise Occupancy
**What it shows:** occupancy per property. **Live. Shown only with 2+ properties.**
**How it's calculated:** each property's occupied/rentable from the live widget, ranked by **empty space**
(most vacant first); green when full, red otherwise.

# TENANT (People)

**Who your tenants are and where they are in their journey.** **Most Tenant blocks are Live** — a snapshot
of today that ignores the filter; only a few count events in the window. Notices live in a separate table
(raised-awaiting-approval vs approved); the confirmed leaving date is set when a manager approves. Filter:
This Month · Last Month · Current FY · Custom · All Time (+ Coming up for forward blocks).

### Tenant Overview
**What it shows:** the people headline. **Mostly Live, one window number.**
**How it's calculated:** live tiles — **Active Tenants** (status 1), **Active / Approved Bookings**,
**Eviction Pending** (notice awaiting approval) / **Eviction Approved**, and two money lines (**Rent at
risk**, **Leaving with dues**). Window tile — **Notices Raised** (notices given in the selected window).

### Move Metrics
**What it shows:** who moved in and out. **Period.**
**How it's calculated:** **Move-ins** = tenants whose joining date falls in the window; **Move-outs** =
tenants whose move-out date (eviction date, else checkout date) falls in the window; **Net change** =
move-ins − move-outs. On Coming up these are scheduled future moves.

### Tenant Journey
**What it shows:** where tenants and bookings are in their lifecycle. **Live bars + a window strip.**
**How it's calculated:** live **Tenants** bars (Under Notice, Approved Eviction, Renewals due in 30 days)
and the **Bookings** funnel over the window (Total → Approved → Cancelled → Converted). The strip below
(Churn, Renewal, Net change) counts the window; the footer shows tenants who left early and average days
taken to raise notice. Coloured by lifecycle: tenants blue, bookings green.

### Verification
**What it shows:** how tenants are verified. **Live.**
**How it's calculated:** among active tenants — **ID Verification** (e-KYC / manually verified / not
verified) and **Police Verification** (done / not done but in time / overdue). Not-verified and not-done
states are red, the rest blue.

### Tenancy Details
**What it shows:** paperwork status. **Live.**
**How it's calculated:** **Rent Agreement** signing (stamp / simple / manually uploaded / not signed) and
**Profile Completion** (completed vs pending) among active tenants.

### Upcoming Eviction
**What it shows:** who's leaving soon. **Live/forward.**
**How it's calculated:** tenants with a notice, bucketed by when they leave (0-7 / 8-15 / 16-30 / 31+ days),
split into **Pending** (awaiting approval) and **Approved**.

### Agreement Expiry
**What it shows:** agreements by how soon they expire. **Live/forward.**
**How it's calculated:** active long-term tenants grouped into **Already expired / 30 / 60 / 90 days /
Valid**, using the same 4-step end-date rule as Occupancy Agreements. Already-expired and 30-day are red.
**Assumption:** where no duration is recorded the agreement is assumed to be 11 months.

### Tenant Profile
**What it shows:** who your tenants are. **Live.**
**How it's calculated:** active tenants by **Gender**, **Age band** (14-22 / 23-35 / 36-50+), and **City**.
Each tab shows a coverage line ("based on N of M tenants who have this recorded") because these fields are
often sparse.

### Tenant Details
**What it shows:** more tenant attributes. **Live.**
**How it's calculated:** active tenants by **Food preference**, **Tenant Type** (student / working…), and
**Institute** (college / company), each with a coverage line; top few + Others.

### Renewal & Retention
**What it shows:** renewals. **One live number, one window number.**
**How it's calculated:** **Renewal Due** *(Live)* = agreements due to renew soon; **Completed** *(Period)* =
renewals done in the window; plus supporting counts (renewal overdue, renewed, stayed after notice).

### Stay Type
**What it shows:** short vs long-term tenants. **Live.**
**How it's calculated:** active tenants split by the short-term flag.

### Renting Type
**What it shows:** renting type split. **Live.**
**How it's calculated:** **interim** — because the renting-type / company fields aren't populated on most
properties, this currently splits by **short-term vs long-term stay** (which is always recorded) so the
card shows real data. It will switch to true B2B/Residential once that field is captured.

### Tenure
**What it shows:** how long tenants have stayed. **Live.**
**How it's calculated:** active tenants grouped by time since joining — under 1 month / 1-3 / 3-6 / 6-12
months / over a year. Bands are half-open so every tenant falls in exactly one.

### Property Wise Active Tenants
**What it shows:** active tenants per property. **Live. Shown only with 2+ properties.**
**How it's calculated:** count of active tenants per property, ranked, each with its share of the account
total.

## Quick answers (support cheat-sheet)

- **A number didn't change when I moved the filter** → it's a **Live** number ("as of today"); Live numbers
  ignore the filter by design (Overdue, Deposit Dues, Occupancy "Now", most Tenant blocks…).
- **The period total looks different from now** → correct; a period shows the window's total, and for
  **Occupancy** a period is the *average across the window's days*, not today's snapshot.
- **Occupancy for last month looks higher than now** → it's a day-weighted average; a fuller earlier part of
  the month pulls it up. Intended.
- **Projected / Upcoming shows money not yet billed** → those are **Forecasts** (rent + recurring packages
  the system will raise before month-end), not current dues.
- **A "by property" card is missing** → those need **2+ properties**; a card with no data shows an empty
  message instead.
- **Collection differs between the two toggles** → Paid Date reads money by when it arrived; Due Date by
  when the bill was due. Same money, two lenses.
- **Under Notice ≠ Upcoming Vacancy count** → Under Notice counts *people*; Upcoming Vacancy counts *rooms/
  beds freeing up* and only future, manager-accepted notices.

# Appendix — the actual queries

The SQL each block runs, with its **source location** so you can always check the live version. `$1` = the
scoped property ids/strings; `$2/$3` = the window's from/to; dates are `YYYY-MM-DD`. Amounts shown short on
screen are the raw invoice/expense amounts here. This is a snapshot — the cited method is the source of truth.

## Shared bases

**Dues base pool** — `src/v1/list_screens/dues/helpers.ts → buildBaseQuery`. Everything in the Dues tab
starts here (unpaid dues owed by active/booking tenants):
```sql
FROM invoices i
JOIN property prop ON (prop.pg_id || 'PG' || prop.pg_number::text) = i.property
LEFT JOIN tenant t ON t.firebase_id = i.payer AND t.property_id = prop.id
WHERE i.property = ANY($1)          -- scoped properties
  AND i.status = 0                  -- not paid
  AND i.amount >= 1
  AND i.is_active = 1
  AND t.status IN (1, 2)            -- active or booking tenant
```

**Collection base** — `src/v1/analytics/collection/collectionService.ts` (COLL_FROM/COLL_WHERE/COLL_AMT):
```sql
FROM payments p
JOIN property prop ON (prop.pg_id || 'PG' || prop.pg_number::text) = p.property AND prop.is_deleted = false
LEFT JOIN payments_invoices pi ON pi.payment = p.id
LEFT JOIN invoices inv ON inv.id = pi.invoice AND inv.is_active = 1 AND inv.status = 1 AND inv.amount > 0
WHERE p.property = ANY($1) AND p.status = 1 AND p.is_active = 1
-- value of each payment (COLL_AMT):
CASE WHEN p.payment_mode IN (211,288,291) THEN 0                         -- adjustments = no new money
     WHEN NOT EXISTS (SELECT 1 FROM payments_invoices pix WHERE pix.payment = p.id)
          THEN (p.net_amount - COALESCE(p.gateway_charges,0))            -- true advance (no bill)
     ELSE COALESCE(inv.amount, 0) END
```

**Occupancy "Now" widget** — `src/v1/list_screens/rooms/helpers.ts → fetchAllWidgetCounts` (shared with the
home screen). Filter codes used: 1401 total rooms · 1409 occupied rooms · 1410 semi-vacant · 1408 vacant
rooms · 1413 overbooked rooms · 1406 booked rooms · 1418 under-notice-with-booking · 1419 disabled rooms ·
1402 under notice · 1415 total beds · 1405 occupied beds · 1403 vacant beds · 1414 overbooked beds · 1420
disabled beds. Rentable = total − disabled.

## Dues — `src/v1/analytics/dues/duesService.ts`

**Overview** (`overviewAggregate`, on the base pool):
```sql
SELECT SUM(i.amount) AS all_time,
  SUM(CASE WHEN i.due_date::date <  :monthStart THEN i.amount ELSE 0 END) AS all_past,
  SUM(CASE WHEN i.due_date::date >= :monthStart AND i.due_date::date <= :today THEN i.amount ELSE 0 END) AS this_month,
  SUM(CASE WHEN i.due_date::date >  :today THEN i.amount ELSE 0 END) AS all_future,
  SUM(CASE WHEN i.due_date::date >= :fyStart AND i.due_date::date <= :fyEnd THEN i.amount ELSE 0 END) AS current_fy,
  SUM(CASE WHEN i.due_date::date >= :lastMonthStart AND i.due_date::date <= :lastMonthSamePoint THEN i.amount ELSE 0 END) AS this_month_prev,
  SUM(CASE WHEN i.due_date::date >= :fyStart AND i.due_date::date <= :today THEN i.amount ELSE 0 END) AS fy_ytd,
  SUM(CASE WHEN i.due_date::date >= :lastFyStart AND i.due_date::date <= :lastFySamePoint THEN i.amount ELSE 0 END) AS fy_ytd_prev
-- FROM buildBaseQuery(...)
```

**Projected Due** (`projectedDueTotal`) = rent still to raise + scheduled packages:
```sql
WITH cfg AS (

       COUNT(*) FILTER (WHERE t.status=0 AND COALESCE(t.date_of_eviction,t.checkout_date)::date BETWEEN $2 AND $3) AS move_outs
FROM tenant t WHERE t.property_id=ANY($1) AND t.status IN (0,1);
```

**Journey → Tenants** live bars:
```sql
SELECT
  COUNT(*) FILTER (WHERE t.status=1) AS headcount,
  COUNT(*) FILTER (WHERE t.status=1 AND t.date_of_eviction IS NULL
        AND EXISTS (SELECT 1 FROM tenant_eviction_details ted WHERE ted.tenant_uuid=t.id AND ted.is_active=1 AND ted.status=2)) AS under_notice,
  COUNT(*) FILTER (WHERE t.status=1 AND t.date_of_eviction IS NOT NULL AND t.date_of_eviction::date >= CURRENT_DATE) AS approved_eviction,
  COUNT(*) FILTER (WHERE t.status=1 AND (t.is_short_term IS NULL OR t.is_short_term=false)
        AND <agreement end date> BETWEEN CURRENT_DATE AND CURRENT_DATE+30) AS renewals_30
FROM tenant t WHERE t.property_id=ANY($1) AND t.status=1;
```
**Journey → Bookings** (`bookingBars`, window): created / approved / cancelled / converted from
`tenant_booking_confirmation`. Footer (`journeyFooters`): renewals in window, left-early count, average days
to raise notice, eviction-pending count.

**Verification** (`getVerification`):
```sql
WITH lk AS (   -- latest verified KYC method per active tenant
  SELECT DISTINCT ON (kh.tenant_uuid) kh.tenant_uuid,
    CASE WHEN lower(kh.verification_document) IN ('aadhaar_otp','aadhaar_otp_digi','aadhaar_esign','pan_otp') THEN 'ekyc' ELSE 'manual' END method
  FROM kyc_history kh WHERE kh.verification_status=1
    AND kh.tenant_uuid IN (SELECT id FROM tenant WHERE property_id=ANY($1) AND status=1)
  ORDER BY kh.tenant_uuid, kh.created_at DESC)
SELECT COUNT(*) base,
  COUNT(*) FILTER (WHERE k.method='ekyc') ekyc,
  COUNT(*) FILTER (WHERE k.method='manual') manual_verified,
  COUNT(*) FILTER (WHERE k.method IS NULL) not_verified,
  COUNT(*) FILTER (WHERE t.police_verification_url IS NOT NULL AND t.police_verification_url<>'') police_done,
  COUNT(*) FILTER (WHERE (t.police_verification_url IS NULL OR t.police_verification_url='') AND t.date_of_joining::date >= CURRENT_DATE-7) police_in_time,
  COUNT(*) FILTER (WHERE (t.police_verification_url IS NULL OR t.police_verification_url='') AND t.date_of_joining::date <  CURRENT_DATE-7) police_overdue
FROM tenant t LEFT JOIN lk k ON k.tenant_uuid=t.id
WHERE t.property_id=ANY($1) AND t.status=1;
```

**Tenancy Details** (`getTenancyDetails`): over active tenants, `LEFT JOIN LATERAL` the latest
`stamp_agreements` row — **Stamp signed** (`stamp_img_url` set), **Simple signed** (no stamp but
`agreement_sign_date` set), **Manually uploaded** (an agreement file url present), **Not signed** (none);
**Profile complete** = a `FILTER` requiring phone, dob, joining date, permanent address, father/mother name &
phone, occupation and local-guardian fields all present.

**Upcoming Eviction** (`getUpcomingEviction`): one row per active tenant with an active notice (latest
`tenant_eviction_details`), bucketed by leaving date (Overdue / 0-7 / 8-15 / 16-30 / 31+) and split by
`ted.status` (2 = pending / 1 = approved).

**Agreement Expiry** (`getAgreementExpiry`): the same 4-step end date as Occupancy Agreements, over active
long-term tenants, into `< today` (expired) / 30 / 60 / 90 / `> +90` (valid).

**Profile** (`getProfile`): over active tenants — **Gender** (`male/female/other` by lower-cased value),
**Age** (from `age(dob)` into 14-22 / 23-35 / 36+, coverage = age ≥ 14), **City** (`perm_district`, top 5 +
Others). Each tab carries a coverage line (recorded ÷ base).

**Details** (`getDetails`): over active tenants — **Food Pref** (`food_preference` matched to pure-veg /
egg / non-veg / no-food), **Tenant Type** (`working_type`, top + Others), **Institute** (`university`).

**Renewal & Retention** (`getRenewalRetention`): **Renewal Due** 🟢 = active long-term tenants whose
agreement ends within 30 days; **Renewal overdue** = agreement already expired; window part = renewals
completed + renewed + stayed-after-notice from `tenant_agreement_renewals`.

**Stay Type / Renting Type / Tenure**:
```sql
-- Stay & Renting type (status 1):
SELECT COUNT(*) FILTER (WHERE t.is_short_term) AS short_term,
       COUNT(*) FILTER (WHERE NOT COALESCE(t.is_short_term,false)) AS long_term
FROM tenant t WHERE t.property_id=ANY($1) AND t.status=1;
-- Tenure (status 1), half-open bands on date_of_joining:
SELECT COUNT(*) FILTER (WHERE t.date_of_joining::date > CURRENT_DATE-30)                                             AS under_1m,
       COUNT(*) FILTER (WHERE t.date_of_joining::date > CURRENT_DATE-90  AND t.date_of_joining::date <= CURRENT_DATE-30)  AS m1_3,
       COUNT(*) FILTER (WHERE t.date_of_joining::date > CURRENT_DATE-180 AND t.date_of_joining::date <= CURRENT_DATE-90)  AS m3_6,
       COUNT(*) FILTER (WHERE t.date_of_joining::date > CURRENT_DATE-365 AND t.date_of_joining::date <= CURRENT_DATE-180) AS m6_12,
       COUNT(*) FILTER (WHERE t.date_of_joining::date <= CURRENT_DATE-365)                                            AS over_year
FROM tenant t WHERE t.property_id=ANY($1) AND t.status=1 AND t.date_of_joining IS NOT NULL;
```
*(Renting Type is an interim short/long-term split because the true renting-type field is unpopulated.)*

**Property Wise Active Tenants** (`getByProperty`, 2+ properties): count of status-1 tenants per property,
ranked, each with its share of the account total.
